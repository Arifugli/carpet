# Переход на 0.8.0 и восстановление

## Обязательные условия

Перед обновлением необходимы **резервная копия PostgreSQL и отдельная копия файлов приватного Storage**. Копия БД должна включать public, Auth, роли/права, последовательности и необходимые настройки проекта. Дамп одних таблиц CRM недостаточен для полного восстановления. Проверьте восстановление на изолированной базе; production URL/ключи не используются в автоматических тестах.

Официальная процедура: [Backup and Restore using the CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Через установленный Supabase CLI сначала проверьте `supabase --help` и `supabase db dump --help`. Соединение берётся из Dashboard → Connect, предпочтительно Session pooler. Пароль хранится локально в менеджере секретов; его не присылают в чат и не публикуют в Git.

Пример для PowerShell, когда `$env:CRM_BACKUP_DB_URL` уже безопасно задан:

```powershell
supabase db dump --db-url $env:CRM_BACKUP_DB_URL -f backup/roles.sql --role-only
supabase db dump --db-url $env:CRM_BACKUP_DB_URL -f backup/schema.sql
supabase db dump --db-url $env:CRM_BACKUP_DB_URL -f backup/data.sql --use-copy --data-only -x storage.buckets_vectors -x storage.vector_indexes
```

Каталог backup создайте заранее вне репозитория/публичных папок. Строки storage.objects и order_photos не являются содержимым фотографий: отдельно скачайте объекты бакета carpet-photos с сохранением путей, сверив число и контрольные суммы. Резервная копия должна оставаться доступной после удаления объектов. До проверки этих копий 0016 не выполняется.

## Порядок выпуска

1. Подготовьте проверенный commit 0.8.0 и остановите запись старого web/worker, входящие формы, телефонию и callback оплаты на согласованное окно. Не оставляйте старую версию работающей между схемой и очисткой. Дождитесь завершения запросов; зафиксируйте резервные копии.
2. Выполните **только read-only** `scripts/cleanup-plan.sql` на текущей БД. Сохраните полный JSON, включая counts и storage_manifest, в приватный файл. Это dry-run: он ничего не удаляет. Список сотрудников с прежними ролями также входит в результат. Сверьте числа непосредственно перед очисткой: они могут изменяться, пока система работает.
3. 0014_workflow_enums.sql — только добавление меток enum; завершите отдельный commit до следующего файла. 0015_order_workflow.sql — схема/RPC/права, деактивация прежних ролей и снимок role_reassignments. Не редактируйте и не переигрывайте 0001–0013. Миграции не выполняются сервером при старте.
4. Отдельно, вручную примените **0016_clear_legacy_orders.sql** целиком, без удаления её BEGIN/COMMIT. Она удаляет все старые заказы, включая корзину, и зависимости. Клиенты/теги/согласия, Auth/сотрудники, филиалы, тарифы/версии, справочники/шаблоны и audit_log сохраняются. Связи calls.order_id обнуляются, сами звонки остаются. Задания/лиды/outbox со ссылкой на заказ удаляются; независимые записи остаются. Сверки кассы и ключи фоновых заданий очищаются как производные старого учёта. Из uses скидок следует убрать удалённые использования; остатки материалов сверяются по оставшимся движениям.
5. Проверьте `maintenance_cleanup_runs` (key=workflow_v2_reset): окончательные counts и манифест. В audit_log добавлено legacy_orders_cleared с русским событием «очистка старых заказов» и числами. Старые записи аудита не изменены. Идентичный повтор 0016 ничего не удаляет и не перезапускает нумерацию. После первого выполнения новый номер начинается с K-1.
6. Разверните новый API и PWA **вместе**, на том же бесплатном Render web. `/ready` должен вернуть 200 и schema=16 через внутренний RPC; без выполненной очистки readiness не зелёный. Проверьте вход admin, назначьте новые роли бывшим сотрудникам и районы/цвет активным водителям. Затем возобновите запись.
7. На тестовом заказе проверьте все передачи, два источника замеров, фото и отложенную доставку. Убедитесь, что anon/authenticated не читают таблицы, а прямое удаление заказа/изменение аудита отклоняется. Запустите Supabase Security/Performance Advisors на целевом проекте.
8. Только после завершения 0016 и проверки сохранённой копии файлов удаляйте старые объекты Storage. Это отдельное действие ниже; оно не запускается сервером или миграцией.

## Механизм очистки и защиты

0016 берёт ACCESS EXCLUSIVE на orders и использует явный список зависимостей; неожиданный FK к orders останавливает миграцию. До удаления сохраняются counts и пути фотографий. Снимаются только запреты DELETE для orders и неизменяемых замеров/событий забора. Триггер audit_log_immutable не снимается. Исходные состояния затронутых триггеров восстанавливаются до commit. При ошибке транзакционный rollback возвращает и данные, и защиту. Права DELETE/TRUNCATE серверной роли не расширяются.

Счётчики клиентов вычисляются SQL, хранимых счётчиков заказов у клиентов нет. Нумерация сбрасывается транзакционным ALTER SEQUENCE RESTART, а не setval. Пустая БД позволяет VALIDATE новых ограничений статусов/источников замеров. Тесты включают успешную очистку с историческими данными, повтор, ошибку внутри удаления и восстановление запретов.

## Storage

Манифест — JSON-массив [{"path":"order_uuid/item_uuid/photo_uuid.jpg"}] или объект с полем storage_manifest. Сохраните его до удаления записей фото. Секреты CLI берёт из SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY в серверном окружении; bucket — carpet-photos.

```powershell
node scripts/cleanup-storage.mjs --manifest=backup/cleanup-plan.json --dry-run
node scripts/cleanup-storage.mjs --manifest=backup/cleanup-plan.json --confirm=delete-legacy-order-photos
```

Без подтверждающего флага выполняется только dry-run. Скрипт проверяет формат каждого пути, соответствие манифесту завершённой 0016 и отсутствие действующих ссылок order_photos. Удаляются только перечисленные объекты, пакетами по 100; повтор допустим после частичного сетевого сбоя. Другие файлы бакета не затрагиваются.

## Откат

До commit ошибка миграции откатывается автоматически (при ручной сессии выполните ROLLBACK). После успешной 0016 старые заказы восстанавливаются из проверенной копии БД и копии Storage; простого отката кода недостаточно. Восстановите копию в изолированное окружение, проверьте Auth, файлы, последовательности и неизменяемый аудит, затем согласуйте переключение. Не смешивайте восстановленные старые заказы с новыми номерами K-1 и далее. Полный аварийный rollback потребует также восстановить старый код/схему и прежние состояния сотрудников из снимка.

## Сохранённые фоновые функции

Worker по-прежнему запускается `npm run worker` с серверными переменными. На выбранном бесплатном размещении отдельный worker не развёрнут; автоматические SLA, напоминания и отправка outbox требуют его отдельного запуска. Новых платных ресурсов этот выпуск не создаёт. Lease/outbox/подписи провайдеров, нормализация телефона и health сохраняются.


## Явный отказ владельца от копий и разовый запуск на Render

Если владелец прямо поручил удалить ненужные старые данные без резервной копии, зафиксируйте это разрешение отдельным событием audit_log. Не предполагайте такой отказ без прямого указания. Для этого выпуска владелец подтвердил удаление без копий 01.11.2026.

После 0014 установите settings.workflow_maintenance=1: триггеры блокируют новые записи и callback провайдеров. 0015/0016 выполняются со своим транзакционным допуском. После нового Live-деплоя установите значение 0. По умолчанию режим выключен; очистка базы никогда не запускается при старте.

Когда ключ Storage доступен только серверу Render, можно явно задать LEGACY_STORAGE_CLEANUP_CONFIRM=delete-legacy-order-photos-0016. При следующем запуске отдельный скрипт finalize-legacy-storage.mjs проверит завершённую 0016, очистит только её манифест через Storage API и запишет аудит и одноразовый маркер. Без точного подтверждения скрипт не удаляет файлы. После успешного запуска очистите переменную окружения. Повтор после завершения безопасен; при ошибке запуск прерывается, и маркер успеха не ставится.

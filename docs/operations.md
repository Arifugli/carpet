# Миграции и восстановление

## Перед выпуском

1. Сделайте и проверьте резервную копию PostgreSQL по процедуре вашего проекта Supabase. Убедитесь, что в копии есть данные `public`, пользователи Auth, нужные роли/права и последовательности. Файлы Storage резервируются отдельно; строки `order_photos` содержат лишь пути. Наличие копии без пробного восстановления не подтверждает работоспособность восстановления.
2. Сначала восстановите копию в отдельный тестовый проект/изолированный PostgreSQL. Нельзя использовать production URL/service_role в автоматических тестах этого репозитория.
3. В короткое окно обслуживания остановите изменения данных. `0003` берёт DDL-блокировки и обновляет только строки, для которых обнаружена прежняя приёмка/стирка без соответствующего признака. На большой БД измерьте длительность на копии заранее.
4. Если это существующая БД, `0001` не выполнять повторно. Выполните `0002_manager_role.sql` и дождитесь завершения/коммита. Затем отдельным запуском выполните `0003_order_lifecycle.sql` целиком. Не оборачивайте обе миграции в одну внешнюю транзакцию.
5. Запустите `npm ci`, `npm test`, затем разверните новый API/статические файлы вместе. Секреты остаются в переменных окружения. `render.yaml` уже использует `npm ci` / `npm start` / `/health`.
6. Выполните ручные сценарии из `testing.md`, прежде чем возобновлять изменения production. Проверьте прямой доступ с anon/authenticated ключом: операционные таблицы должны быть недоступны; API с активным профилем должен работать.

## Проверка после миграции

Сравните количество orders/order_items/order_photos/status_history до и после: миграция не удаляет строки. Для прежних cancelled причина может быть NULL — это сохранённые исторические данные.

```sql
select count(*) from public.orders;
select count(*) from public.order_items;
select count(*) from public.order_photos;
select status, count(*) from public.orders group by status;
select count(*) from public.orders where deleted_at is not null;
select code,name_ru from public.cancel_reasons order by position;
select entity,action,count(*) from public.audit_log group by entity,action;
```

На тестовой БД повторно выполните только `0002` и `0003`: схема/данные не должны дублироваться. Проверка advisors выполняется в выбранном проекте Supabase после применения; здесь она не запускалась, поскольку целевой проект не указан.

## Если выпуск неудачен

При ошибке `0003` её транзакция откатывается целиком; добавленная `manager` в `0002` остаётся безопасным расширением enum. Сохраните ошибку и исправьте миграцию на тестовой копии. Не удаляйте новые поля/аудит ради возврата старого API.

После успешной миграции нельзя откатывать **только** приложение на исходную версию: её запросы не исключают корзину, а права/RPC изменены. Предпочтительно исправление новой версии вперёд либо возврат совместимой версии с фильтрацией `deleted_at` и теми же правилами отказов. Если необходим полный аварийный возврат, остановите записи, сохраните все новые события/данные, восстановите проверенную резервную копию в отдельный проект, сверяйте данные и переключайте конфигурацию только после проверки. Такое восстановление не выполняется автоматически этим проектом.

## Пробное восстановление резервной копии

1. Разверните отдельное окружение с совместимой версией PostgreSQL/Supabase и приватным Storage.
2. Восстановите дамп штатной процедурой Supabase либо согласованным `pg_restore` для вашей схемы резервирования. Формат дампа, права на Auth/storage и доступ к управляемым схемам зависят от выбранного способа; не запускайте общий restore поверх работающего проекта.
3. Восстановите объекты Storage, сравните контрольные суммы/пути, проверьте несколько подписанных фото.
4. Сверьте количества, диапазон кодов, последовательности, общие суммы и число отменённых/удалённых заказов. Убедитесь, что новый номер не конфликтует с восстановленными номерами.
5. Подключите тестовый API отдельными env-переменными, проверьте вход, создание, отказ, корзину, восстановление, аудит, трекинг. Зафиксируйте время восстановления и дату проверенной копии.

## Хранение и производительность

Автоматической физической очистки нет. API не имеет обхода soft delete, TTL или purge-флага. Очистку можно проектировать только после согласования срока хранения, состава резервной копии и правила сохранения аудита — отдельной обслуживающей ролью/процедурой, без предоставления DELETE обычному service_role.

Для отчётов используйте `active_orders` или обязательный `deleted_at is null`; отказы берите из `cancelled_orders`. Не используйте raw `orders` без фильтра. Оба представления `security_invoker`, доступны серверу.

Списки ограничены 100 строками и используют курсор. Есть частичные индексы активных заказов/корзины, индексы автора удаления и аудита. Перед утверждением SLA нагрузите копию 50 тыс. заказов реальными фильтрами и измерьте HTTP p95; при необходимости используйте EXPLAIN ANALYZE и отдельный индекс под фактический поиск. Встроенные ограничители запросов работают на один процесс; несколько инстансов требуют общего хранилища лимитов.

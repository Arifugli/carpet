# Этап 4: рабочие операции и интеграции

Миграция `0007_business_operations.sql`, API и русские экраны продолжают существующую модель. Оплаты, скидки, склад, начисления и ограничения мощности выполняются в SQL. Опубликованные миграции 0001–0006 сохранены.

## Принятые правила

| Возможность | Реализация |
|---|---|
| Оплата | Предоплата/частичная/при выдаче — положительные проводки до суммы долга. Cash подтверждается сразу, безнал водителя/диспетчера — после проверки. Payme/Click подтверждаются только callback провайдера. |
| Возврат | Отдельная проводка, администратор, в пределах оплаченного выбранным способом. Онлайн-возврат — через провайдера. След оплаты остаётся после полного возврата. |
| Касса | День Asia/Tashkent, ожидаемая сумма, сдано, разница, причина и подтвердивший. Сверяет admin/dispatcher. После сверки новые наличные проводки данного получателя за этот день запрещены. |
| Документы | Внутренняя квитанция, акт приёма со снимком состава/фото/дефектов; печать в браузере. Квитанция не заменяет фискализацию у платёжного провайдера. |
| Скидки | Промокод либо накопительная скидка по числу выданных заказов. Правила admin: скидка до 50%, срок, минимум суммы/заказов, общий лимит. Применяет operator/admin, один раз до стирки, без сочетания с пенсионной скидкой. Доставка не дисконтируется. Снимок правила сохраняется; лимит не освобождается при последующем отказе. |
| Приёмка | Сотрудник/водитель создаёт акт, отправляет SMS-код. Подтверждение клиентом: 6 цифр, 5 минут, 5 попыток, повторная отправка через 2 минуты. Неудачные попытки сохраняются. Токен акта — 24 случайных байта; OTP — HMAC, текст очереди зашифрован AES-GCM. Цех не получает токен акта. |
| Претензии | Причина, фото уже загруженных ковров, ответственный, срок. Admin утверждает повторную стирку, скидку в пределах долга, компенсацию или отсутствие нарушения. Компенсация имеет отдельную отметку выплаты. |
| Повторная стирка | Отдельное задание received→washing→drying→quality_check→packing→ready, с учётом химии и аудита. Первоначальная выдача сохраняется. При завершении претензия закрывается. |
| Планирование | Лимит окна филиала, дополнительный лимит дня/района, мощность цеха в м². Создание и перенос сериализованы блокировками. Подсказка ближайшего свободного окна на 14 дней. Порядок объезда — район→окно→позиция, карта из этапа 2. |
| QR | Сервер генерирует SVG QR для K-номер-позиция; печатная форма 58×40 мм. Сканирование и ручной ввод работают у водителя/цеха. |
| Склад | Материал/единица/норма на м². Приход/корректировка admin, чтение цехом. Начало стирки автоматически списывает норму. Недостаток откатывает этап и все движения. Повторная доставка запроса не списывает дважды. |
| Мотивация | История ставок по филиалу/роли/событию, за заказ или м². Завершённые визиты и стирка/упаковка создают начисления со снимком роли, единицы и ставки. Повторная стирка по претензии по умолчанию без дополнительного начисления. KPI оператора — заявки/отказы/выдачи. Оклад, налоги и выплата зарплаты не моделируются. |
| Филиалы | Собственные сотрудники, тарифы, параметры, справочники, мощности, нормы и ставки; фильтры отчётов. Новому филиалу администратор настраивает источники/окна/районы и шаблоны. Клиент по телефону общий для компании. |
| Клиенты/SLA | Теги, согласия SMS/Telegram, чёрный список с причиной (только admin). Создание заказа для заблокированного клиента запрещено SQL. Worker создаёт по одному напоминанию о просроченном заказе/претензии каждому руководителю; раздел «Просрочки и эскалации». Закрытые эскалации завершаются автоматически. |

## Подключение провайдеров

Все ключи перечислены в `.env.example`. Без ключей адаптеры выключены. Настройка выполняется в окружении web/worker, значения не передаются браузеру и не пишутся в Git.

Payme: `PAYME_KEY`, `PAYME_MERCHANT_ID`, account-поле кассы `intent_id`. Callback `/api/providers/payme`, Basic `Paycom:key`, JSON-RPC CheckPerformTransaction/CreateTransaction/PerformTransaction/CancelTransaction/CheckTransaction/GetStatement. В API Payme суммы в тийинах, в CRM — целые сумы; SQL проверяет обе величины. Счёт хранится до callback, переходы/повторы атомарны, таймаут 12 часов. Для выданного заказа автоматическая отмена возвращает -31007. Настройка должна пройти [песочницу Payme](https://developer.help.paycom.uz/pesochnitsa/). [Параметры ссылки оплаты](https://developer.help.paycom.uz/initsializatsiya-platezhey/otpravka-cheka-po-metodu-get/).

Click: `CLICK_SECRET`, `CLICK_SERVICE_ID`, `CLICK_MERCHANT_ID`. Callback `/api/providers/click`, форма Prepare/Complete, подпись MD5 по полям протокола, постоянный числовой prepare_id, проверка суммы/счёта. [Документация Click](https://docs.click.uz/). Подробная страница текущего Shop API при разработке была недоступна через просмотрщик; перед активацией требуется сверить контракт в кабинете и пройти тесты мерчанта. Локальные контрактные тесты не считаются сертификацией провайдера.

SMS: `ESKIZ_TOKEN`, `ESKIZ_FROM`; адаптер POST notify.eskiz.uz/api/message/sms/send. Token задаётся и обновляется оператором инфраструктуры. Тексты шаблонов/OTP необходимо проверить в аккаунте Eskiz. Telegram: `TELEGRAM_BOT_TOKEN`, клиент предварительно запускает бота; сотрудник указывает chat_id и согласие. Используется официальный [sendMessage](https://core.telegram.org/bots/api#sendmessage). Автоматическое получение chat_id ботом не реализовано.

Согласия по умолчанию выключены. Обычные сообщения требуют согласия клиента, повторно проверяемого перед отправкой; OTP отправляется по явному запросу приёмки. Истёкший OTP, отменённый забор, устаревший статус или удалённый заказ пропускаются. SMS/Telegram могут доставляться повторно при потере ответа провайдера: очередь обеспечивает доставку как минимум один раз, а не гарантированную однократную отправку. `sent` означает принятие провайдером, не подтверждение получения клиентом.

`PUBLIC_BASE_URL` формирует ссылки на статус и оценку. `OTP_SECRET` — случайный секрет HMAC. `NOTIFICATION_ENCRYPTION_KEY` — 32 случайных байта в hex, одинаковые у web/worker. Не меняйте этот ключ при наличии неотправленных OTP; после ротации запросите новые коды.

## Очередь и внешний API

`npm run worker` запускает обработчик PostgreSQL outbox без Redis. Он выполняет SLA/напоминания, арендует задания через SKIP LOCKED, использует lease token, повторы с задержкой до 1 часа и прекращает автоматические попытки после 8 ошибок. Admin может повторить запись в разделе интеграций. SIGTERM останавливает получение новых заданий; незавершённая аренда возвращается в обработку через 2 минуты. По умолчанию `WORKER_SEND_ENABLED=false`: сообщения не отправляются. Включайте только с настроенными каналами.

Webhook-подписки: HTTPS, точный allowlist `WEBHOOK_ALLOWED_HOSTS`, секрет берётся из указанной переменной `WEBHOOK_SECRET_*`. Проверка публичного IP выполняется при DNS lookup фактического соединения; redirects запрещены. Тело содержит уникальный `id`, событие, код/id заказа, статус и время. Заголовки: X-CRM-Event-Id, X-CRM-Timestamp, X-CRM-Signature, Idempotency-Key. Подпись HMAC-SHA256(secret, `timestamp + '.' + rawBody`). Получатель сверяет подпись/срок и дедуплицирует по `id`; повторы могут приходить позже следующих событий.

Входящие формы: `/api/integrations/orders`, `EXTERNAL_FORM_SECRET`, `EXTERNAL_FORM_ACTOR_ID` активного оператора отдельной интеграции. Обязателен UUID Idempotency-Key. HMAC включает ключ: `timestamp + '.' + idempotencyKey + '.' + rawBody`. Время — Unix seconds, допустимое расхождение 5 минут. Payload соответствует обычному созданию заказа; SQL проверяет права сервисного сотрудника и филиал. Контактные формы сайта/Instagram/Telegram вызывают этот единый адаптер с сервера; секрет не размещать в публичном JS.

Телефония: `/api/integrations/telephony`, `TELEPHONY_SECRET`, `TELEPHONY_ACTOR_ID`. HMAC: `timestamp + '.' + rawBody`. Нормализованный payload: external_id, branch_id, phone +998…, direction in/out, outcome ringing/answered/missed/no_result, recording_url HTTPS и order_id необязательны. external_id обновляет один звонок; устаревшее ringing не отменяет завершение. Оператор видит уведомление и карточку клиента при опросе раз в 10 секунд, пропущенные — в журнале. Запись можно привязать к заказу через call.link. Конкретная АТС преобразует свой webhook в этот контракт.

## Импорт и экспорт

CSV UTF-8 или первый лист XLSX, до 100 строк/2 МБ. Сначала образец и preview, затем отдельная кнопка записи; SQL фиксирует весь пакет либо откатывает его целиком. Один ключ не создаёт дубликаты. Заказы импортируются новыми с текущей ценой SQL; исторические delivered/paid значения не подделываются. Колонки clients: name,phone,address. Orders: дополнительно pickup_date и length_m,width_m,tariff либо items (JSON-массив ковров). Флаги — true/false или 1/0. Даты ISO YYYY-MM-DD; поддержаны также числовые Excel-даты со стилем даты. Формулы, макросы, внешние ссылки, объявления XML-сущностей и большие архивы отвергаются.

CLI: `node scripts/import.mjs --file clients.xlsx --kind clients --branch UUID --url https://CRM`; токен admin через `CRM_ACCESS_TOKEN`. Без `--commit` только проверка; для фиксации добавьте `--commit --key UUID`. Экспорт клиентов CSV/XLSX — admin/manager, страницы по 1000 строк и X-Next-Cursor. CSV защищён от формул, для обратного импорта используйте образец или XLSX/CSV с исходными телефонами.

## Ручная приёмка

1. Создайте правило 10%, примените к новому заказу оператором. Проверьте SQL-цену и снимок. Повтор с тем же ключом даёт ту же скидку; другой ключ повторно скидку не добавляет.
2. Примите частичную оплату, проведите безналичную через проверку, распечатайте квитанцию/QR. Сверьте кассу водителя; попробуйте повторно принять наличные после закрытия дня.
3. Загрузите фото/дефекты, создайте акт, запросите SMS на тестовом номере. Проверьте акт по клиентской ссылке и подтвердите код. Неверный код увеличивает попытки, истёкший/пятый неверный блокирует подтверждение.
4. После выдачи зарегистрируйте претензию. Admin назначает повторную стирку; цех проходит отдельную очередь. Исходный заказ остаётся delivered. Проверьте расход химии и завершение претензии.
5. Укажите норму, попробуйте начать стирку при недостатке. После прихода повторите с тем же ключом, проверьте единственное списание и начисление по ставке. Manager видит начисления, но не меняет нормы/ставки.
6. Заполните окно района и суточную мощность. Новый заказ/назначение сверх лимита отклоняются, ближайшая подсказка предлагает доступную дату. Проверьте другой филиал.
7. Выполните preview CSV и XLSX, затем commit дважды с одним ключом. Для ошибочного пакета проверьте отсутствие частичного импорта. Импортируйте несколько ковров через items.
8. Отправьте подписанный входящий/пропущенный звонок. Проверьте popup, историю клиента, запись и привязку к заказу. Попытка с неверной подписью — 401.
9. На тестовом стенде включите worker/каналы, проверьте opt-in, повтор после ошибки, dead/retry, пропуск старого статуса и истёкшего OTP. Закройте просроченный заказ/претензию — эскалация завершится на следующем tick.

Автоматически проверяются SQL, HTTP, DOM, подписи, повторы, OTP и форматы экспорта. Реальные аккаунты/песочницы, браузерная печать на физическом термопринтере и производственные Supabase/Render в этом запуске не проверялись.

## Приёмка и фото 0.7.0

Пять комплексных сценариев проверяют цену у водителя, оплату до приёма цехом, сохранение согласованной цены при повторном замере, отдельные шаги передачи, обязательные замеры/фото, идемпотентность, запрет обхода через старый status/visit API и атомарность пакета замеров. Отдельно моделируется обновление работающей 0.6: замер уже забранного заказа снова доступен, старые суммы/фото сохраняются. HTTP проверяет просмотр всех фотографий клиента любой из шести ролей филиала, отказ постороннему филиалу, приватные ссылки и страницы галереи. Отсутствующий объект Storage нельзя зарегистрировать как успешно загруженный.

DOM → HTTP → SQL воспроизводит весь процесс: водитель вводит размеры/подтверждает штуки, получает цену, загружает фото через очередь, открывает свёрнутую по умолчанию галерею, отмечает «Забрал» и «Передал цеху»; цех нажимает «Принял», вводит независимые размеры и начинает стирку. Реальная камера на телефоне и внешний маршрут в этом автоматизированном сценарии заменены локальными адаптерами.

## Заказы и замеры 0.6.0 (первоначальная модель; цена/передача изменены в 0.7)

Четыре новых комплексных сценария покрывают регионы/районы, структурированный адрес, количество и единицы, неизвестную площадь, независимые замеры, объяснение расхождений, идемпотентность, замороженную ставку, запреты изменения после оплаты/стирки, права на историю и её неизменность. DOM → HTTP → SQL проверяет создание без размеров, ввод замера водителем, повторный замер цехом и расчёт итоговой цены; карта доступна только водителю и удаляется при выключении.

Исторические сценарии используют локальную функцию `test_legacy_order`, создающую измеренный заказ через прежнюю модель. Она существует исключительно в тестовом PGlite и отсутствует в рабочих миграциях. Новые сценарии используют настоящее создание через `create_order_audited` и HTTP.

Автоматизированный браузер недоступен в локальном окружении (EPERM). Реальное построение дороги картографическим сервисом и разрешение геолокации на телефоне требуют ручной приёмки; DOM проверяет роли, URL, переключатель и сохранение письменного адреса.

## Ручная приёмка на тестовом Supabase

Подготовьте отдельные активные учётные записи admin, manager, operator, driver, workshop. Примените миграции, настройте `.env`, запустите сервер. Для каждого действия ниже проверьте событие в «Журнале аудита»: автор, роль, время Ташкента, IP и before/after.

1. **Отказ.** Войдите оператором, создайте заказ, откройте карточку → «Отказ клиента». Пустой комментарий/причина не отправляются. Выберите «Дорого», заполните комментарий, укажите нули и сохраните. Заказ остаётся в списке с `cancelled`, причина и суммы доступны в карточке.
2. **Заявка.** Для нового заказа нажмите «Запросить удаление», укажите причину. Заказ остаётся в списке, есть пометка ожидания. Оператор не видит кнопки удаления, корзины и аудита. Повторная заявка отклоняется. Войдите администратором, найдите её в «Заявках на удаление».
3. **Удаление.** Администратор открывает этот заказ → «В корзину» → обязательная причина. После сохранения заказ исчезает из обычного списка и истории клиента. Его обычная карточка API даёт 404. Публичная ссылка `/track/<token>` показывает нейтральное сообщение без указания факта удаления.
4. **Корзина.** Войдите администратором или руководителем. Найдите заказ по удалившему, дате и фрагменту причины. Проверьте код, клиента/телефон, адрес, состав, сумму, статус удаления, имя удалившего и время. У оператора/водителя/цеха запрос GET `/api/trash` с их токеном даёт 403.
5. **Восстановление.** В корзине нажмите «Восстановить». Заказ исчезает из корзины, возвращается в список с прежним кодом, составом и статусом. Если до удаления он был cancelled, остаётся cancelled. Публичная ссылка снова доступна. `restored_at/by` записаны; прежняя причина и снимки доступны в аудите. Повторите цикл и проверьте два события удаления/восстановления.
6. **Защита после стирки.** Создайте заказ, назначьте активного водителя (`PATCH /orders/:id/driver`), переведите последовательно new → pickup_assigned → received → washing через `/status`. Оператор не может отменить/запросить удаление после new. Администратор тоже не может удалить washed-заказ: 409. Верните в received; запрет остаётся. Отказ admin/manager разрешён с обязательными суммами, включая 0.
7. **Оплата.** В карточке заказа администратором примите 1000 сум наличными. Удаление запрещено. Оформите возврат 1000 сум тем же способом; paid_amount станет 0, след оплаты остаётся, удаление всё ещё запрещено. При отмене новая сумма `payment_amount` прибавляется к текущей, не заменяет её.
8. **Закрытый заказ.** Последовательно доведите другой заказ до delivered. Отказ и удаление отклоняются. Прямая попытка POST `/status` со значением cancelled даёт 400, SQL legacy RPC также не позволяет обходить причину.
9. **Права и аудит.** Водитель видит только назначенные ему заказы, цех только свои этапы и маску телефона. С их токенами запросы удаления, восстановления и аудита дают 403. SQL `UPDATE/DELETE/TRUNCATE audit_log` от service_role отклоняется; триггер блокирует такие команды и от владельца таблицы без изменения схемы. Проверяйте это только на тестовой БД.
10. **Цена и повтор создания.** Измените размеры/тариф/флаги в форме, нажмите «Рассчитать цену»: ответ приходит из SQL. Отправьте два одинаковых POST `/orders` с одним UUID Idempotency-Key: должен вернуться тот же id. Изменённые данные с прежним ключом дают 409. В базе один заказ и одно событие его создания.

Проверки скорости и резервного копирования требуют отдельной тестовой копии с реалистичным объёмом, см. `operations.md`. Текущие индексы и курсор созданы, но SLA 300 мс без замера не заявляется выполненным.

# Этап 2 — рабочие места

## Состав

Новые миграции: `0004_dispatcher_role.sql` отдельно фиксирует enum; `0005_workspaces.sql` добавляет филиалы, роль-права, справочники, адреса клиентов, обращения, звонки, напоминания, задания/визиты, события цеха и дефекты, минимальный реестр оплат, версии тарифов/параметров и шаблоны уведомлений. `0001`–`0003` не меняются.

Матрица: `config/permissions.json`; API читает её при запуске. В SQL находится сгенерированная копия, равенство проверяет тест. Для изменений уже выпущенной матрицы нужна новая миграция. `scripts/sync-permissions.mjs` предназначен для синхронизации исходника перед первым применением соответствующей миграции, а не для переписывания истории БД.

Выбрана лёгкая PWA без сборки: существующий Express раздаёт ES-модули и Service Worker. Это сохраняет архитектуру проекта, уменьшает объём загрузки на телефоне и позволяет отдельно развивать очередь при плохой связи. Service Worker кеширует только оболочку — API и публичные ссылки не кешируются. IndexedDB хранит снимки заданий и очередь конкретного сотрудника; JWT, пароли и service_role в очередь не записываются. Выход очищает снимки, незавершённые действия сохраняются за прежним сотрудником и не отправляются от другой учётной записи.

## Экраны

- Оператор: быстрый ввод с поиском по телефону, карточка/адреса и история, повторный заказ через заполненную форму с актуальным SQL-превью; обращения без заказа с причинами отказа, журнал звонков и перезвоны.
- Диспетчер: забор/доставка по дате и окнам, районы, назначение/перенос, причины проблем, число активных заданий на водителя, карта точек и порядок визитов. Для карты нужны координаты заказа. Линия обозначает порядок визитов, не дорожный маршрут; навигация открывает карты по адресу/координатам.
- Водитель: свои задания выбранного дня, звонок/навигация, выезд/забрал/доставил, проблема визита, оплата и фото. При плохой связи действия и JPEG-фото попадают в очередь. Денежная запись не считается подтверждённой сервером до синхронизации.
- Цех: приоритет срочных, приёмка → стирка → сушка → контроль → упаковка → готовность, исполнитель и время события, дефекты, фото, QR-сканирование с ручным вводом как запасным способом. Контроль и упаковка — `production_stage` внутри статуса drying; старый граф order_status сохранён.
- Администратор: создание учётной записи, роли/филиал/активность, одноразовая ссылка восстановления доступа, справочники, филиалы, шаблоны, история тарифов/параметров и дата вступления в силу. Ссылка не отправляется сотруднику автоматически.
- Руководитель: прежнее чтение, корзина и аудит; отчётные экраны и экспорт описаны в stage3.md.

## Правила

Администратор и руководитель видят все филиалы; остальные ограничены своим филиалом, водитель дополнительно назначением, цех — этапами. Проверки повторяются в SQL. Клиентская карточка общая для компании по уникальному телефону, но история заказов оператора фильтруется филиалом. Новые филиалы получают копию исходных справочников для последующей настройки.

Действия имеют обязательный Idempotency-Key UUID и транзакционную квитанцию результата. Повторные данные с тем же ключом возвращают результат, иной payload отклоняется. В заданиях и цехе дополнительно передаётся ожидаемое состояние: устаревшие офлайн-действия требуют проверки, а не применения к новому этапу. При конфликте очередь останавливается и сохраняет действие для сотрудника.

Оплата наличными подтверждается сразу. Отметка терминала/перевода от водителя ожидает проверки администратора/диспетчера. Повтор и переплата защищены SQL. Провайдерские Payme/Click, возвраты, чеки и сверка кассы — этап 4. Старые суммы этапа 1 перенесены в ledger как legacy; оплата при отказе также отражается в нём.

Тарифы выбираются в SQL по филиалу и effective_at, исходная цена созданного заказа сохраняется в pricing_snapshot. Будущие версии не меняют текущий расчёт; версия филиала имеет приоритет над глобальной. Активность и роли берутся из profiles при каждом запросе; последнего администратора нельзя отключить.

## Ручная проверка

1. Применить 0004, затем 0005. Назначить активного dispatcher и филиал, подготовить driver/workshop того же филиала.
2. Оператором найти клиента по +998, открыть адреса/историю, нажать «Повторить заказ» и проверить превью цены. Создать обращение «Перезвонить» и проверить напоминание.
3. Диспетчером назначить забор, выбрать день/окно/район/водителя, проверить карточку и нагрузку. Перенести с причиной; старое задание должно остаться в истории. Заполненное окно не принимает сверхлимитное задание.
4. Водителем выбрать нужный день, отметить «Выехал», затем «Забрал». Отметить наличные и терминал: только наличные сразу увеличивают paid_amount. Подтвердить терминал диспетчером в карточке → «Оплаты».
5. Отключить сеть, выполнить действие; открыть «Очередь отправки». Подключить сеть, проверить один результат. Повторить с изменившимся серверным состоянием: действие должно остаться на проверку. Сменить пользователя — чужая очередь не видна и не отправляется.
6. Цехом сканировать K-…-1 либо ввести вручную. Пройти все этапы, зафиксировать дефект и фото. Перескочить контроль/упаковку ролью workshop нельзя.
7. Администратором создать неактивного сотрудника, назначить роль/филиал, активировать. Ввести будущий тариф, проверить прежнюю текущую цену и историю. Восстановление доступа создаёт ссылку для безопасной передачи, не письмо.

Автоматически проверяются SQL, HTTP/DOM-сценарии и настоящая IndexedDB-очередь через fake-indexeddb. Камера, установка PWA, хранение под давлением памяти телефона, визуальная карта и реальный Supabase Storage требуют проверки на целевых устройствах; успешный DOM-тест её не заменяет.

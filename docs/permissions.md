# Права — этапы 1–4

Исходник матрицы: `config/permissions.json`; `src/permissions.js` читает его при запуске. SQL-функции проверяют активность сотрудника, полномочия и состояние заказа внутри транзакции; тест сверяет SQL-копию матрицы. Условные переходы и запреты хранятся в БД. `admin` не обходит финансовые запреты и защиту аудита.

## Дополнение этапа 2

`dispatcher`: чтение в своём филиале, назначение, логистические статусы, доска/перенос заданий, звонки, задачи, фото и приём/проверка оплат. Доступа к корзине, журналу, тарифам и управлению сотрудниками нет. Driver ограничен своим заданием и филиалом, workshop — этапами цеха и филиалом.

Operator/admin получают clients/leads/calls/tasks; dispatcher — calls/tasks. Назначать задачи другим сотрудникам могут admin/dispatcher, остальные — себе. Workshop/admin проходят производственные этапы, отмечают дефекты и фото. Оплаты доступны admin/dispatcher/driver; отметки терминала/перевода водителя требуют подтверждения admin/dispatcher. manager остаётся читателем, помимо явно оговорённых действий этапа 1; reports/exports/payroll реализованы; руководитель читает их без редактирования операционных данных.

Admin управляет staff/catalogs/branches/tariffs/templates. Последний активный admin защищён SQL. Для неуправленческих ролей требуется филиал, сервер загружает его из профиля при каждом запросе. API создание/смена статуса/отказ/фото не позволяют пересекать филиалы; прямой доступ клиентских ключей к новым таблицам закрыт.

| Действие | admin | manager | operator | driver | workshop |
|---|---|---|---|---|---|
| Список/карточка | Все активные | Все активные | Все активные | Только свои активные | Активные на этапах цеха |
| Создание | Да | Нет | Да | Нет | Нет |
| Превью цены | Да | Да | Да | Нет | Нет |
| Назначить водителя | Да | Нет | Да | Нет | Нет |
| Обычный статус | По графу БД | Нет | По графу БД | Свои: received/delivering/delivered | washing/drying/ready |
| Отказ клиента | До delivered | До delivered | Только new | Нет | Нет |
| Заявка на удаление | Прямое удаление | Прямое удаление | Только new, без оплаты/стирки | Нет | Нет |
| Мягкое удаление | Да, без оплаты/стирки | Да, без оплаты/стирки | Нет | Нет | Нет |
| Корзина/восстановление | Да | Да | Нет | Нет | Нет |
| Аудит: чтение | Да | Да | Нет | Нет | Нет |
| Аудит: изменение/удаление | Нет | Нет | Нет | Нет | Нет |
| Загрузка/регистрация фото | Активные заказы | Нет | Активные заказы | Только свои | Только этапы цеха |
| Изменение тарифов | Да | Нет | Нет | Нет | Нет |

Цех видит `received`, `washing`, `drying`, `ready`; полный телефон заменён маской, публичный токен ему не выдаётся. Удалённые заказы недоступны через обычную карточку даже руководителю; для них предназначен `/trash/:id`.

После `cancelled` и `delivered` обычный статус не меняется. Восстановление из корзины сохраняет `cancelled`, если заказ был отменён до удаления. Удаление не является новым статусом.

Стирка считается начатой при `washing` и последующих этапах либо записи этих статусов в истории. Признаки `washing_started_at` / `payment_recorded_at` сохраняются после шага назад и обнуления текущей суммы. Поэтому возврат статуса не разрешает удаление. `received` без стирки и оплаты можно удалить.

В БД `audit_log` закрыт от `UPDATE/DELETE/TRUNCATE` правами и триггером. Приложение не выполняет физический `DELETE orders`; он также запрещён правами и триггером. Суперпользователь/владелец схемы является внешним административным контуром и может менять саму схему — роль `admin` приложения таких полномочий не имеет.

Прямое чтение операционных таблиц для `anon`/`authenticated` отозвано. Доступ проходит через API с service_role на сервере. Роль берётся из активного `profiles`, а не из пользовательских metadata JWT. Новая `manager` добавлена только ради полномочий этапа 1; `dispatcher` остаётся задачей этапа 2.

## Отчёты

`reports` и `exports` есть только у admin/manager. `visit.arrived` доступен admin/dispatcher/назначенному driver по разрешению status, в своём филиале. Роли цеха и оператора не получают доступ к отчётам.

## Этап 4

| Действие | Кто | Дополнительные ограничения SQL |
|---|---|---|
| Применить скидку | admin/operator | Только правило своего филиала, до стирки, один раз; цена не ниже оплаты |
| Правила скидок, возвраты, решения претензий, компенсации | admin | Финансовые лимиты, нельзя вручную подтвердить Payme/Click |
| Претензия | admin/operator | Свой филиал, фото своего заказа |
| Повторная стирка | admin/workshop | Специальное задание, свой филиал; исходный delivered сохраняется |
| Акт/запрос SMS | admin/operator/dispatcher/назначенный driver | При приёмке; цех не получает клиентский токен |
| Касса | admin/dispatcher/driver | Driver видит свою; сверяет admin/dispatcher |
| Склад | admin/workshop | Цех читает; нормы/приход/корректировку изменяет admin |
| Ставки | admin | Будущая дата; начисления сохраняют снимок |
| Начисления/KPI/экспорт клиентов/SLA | admin/manager | Чтение, фильтр филиала |
| Планирование | admin/dispatcher/operator | Operator читает подсказки; лимиты/назначения — admin/dispatcher |
| Webhook/outbox retry/import | admin | Подписи, allowlist, атомарный импорт |
| Теги/согласия | admin/operator | Свой клиент/филиал; чёрный список — admin |
| QR | Сотрудники с read | Обычный scope заказа; цех без финансовых документов |
| Привязка звонка | admin/operator/dispatcher | Звонок и заказ одного доступного филиала |

Системные RPC provider/outbox/tick закрыты от PUBLIC/anon/authenticated. HTTP callback имеет отдельную проверку подписи провайдера; внешний intake/телефония — HMAC и отдельного активного сотрудника интеграции. Клиентский акт/оценка защищены случайным токеном и ограничителем попыток. Все новые таблицы RLS, права выдаются только серверному service_role.

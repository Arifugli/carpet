# Решения и допущения

## План этапа 1

Таблицы: расширение `orders`, новый `cancel_reasons`, `audit_log`, `order_creation_keys`; использование существующих `profiles`, `clients`, `order_items`, `order_photos`, `status_history`, `tariffs`. Новая роль `manager` — отдельной миграцией enum. Эндпоинты: отказ, заявка на удаление, soft delete, корзина, восстановление и аудит; фильтрация существующих чтений. Экраны: вход, заказы/карточка, формы действий, очередь заявок, корзина и аудит. Тесты: SQL, HTTP, полный сценарий интерфейса; затем обновление README/API/прав.

## Неоднозначности, разрешённые до реализации

1. Фразу «оператор может отменять (A) и отправлять заказ на удаление только в статусе new» трактуем как ограничение **обоих** действий статусом `new`. Администратор/руководитель отменяют любой ещё не закрытый заказ до `delivered`. Оператор не выполняет фактическое удаление.
2. Руководителю нужна корзина уже на этапе 1, поэтому `manager` вводится сейчас. Он получает только явно нужные действия: чтение, превью цены, отказ, корзина/восстановление и аудит. Общие редакторские права оператора ему не наследуются.
3. «Стирать нельзя удалять» проверяется по истории, а не только текущему статусу. `washing` и более поздние этапы навсегда ставят `washing_started_at`. При миграции используется существующая история. `received` означает приёмку в цех, но ещё не начало стирки.
4. Старая схема не содержит оплат. Добавлена минимальная `paid_amount`, неизгладимый признак `payment_recorded_at` и отдельная сумма новой оплаты при отказе. Полный платёжный модуль не реализуется на этапе 1.
5. Причина и непустой комментарий обязательны при каждом новом отказе. После приёмки в цех обязательны обе суммы, включая явный ноль. Суммы — целые сумы, исходная цена заказа не заменяется стоимостью фактически выполненной работы.

## Данные и безопасность

- `0001_init.sql` не изменён. `0002` фиксирует enum отдельной транзакцией; `0003` транзакционна и повторяема. Нумерация `0002_` / `0003_` следует явному требованию пользователя; CLI Supabase в окружении отсутствует, миграции созданы как файлы и проверены исполнением SQL.
- Исторические `cancelled` без причины сохраняются без придуманной причины и автора. Для старых записей эти поля могут быть NULL. Новые отказы проходят строго через `cancel_order`; старый `change_order_status(...,'cancelled',...)` отклоняется.
- «Четыре действия» в критериях: `cancelled`, `deletion_requested`, `deleted`, `restored`. Дополнительно аудируются создание, обычные статусы, назначение водителя, клиенты, ковры, фото, тарифы.
- Отказ является бизнес-событием и остаётся в рабочих данных. Корзина — отдельный признак. Физическое удаление не предоставляется API. Процедура очистки по сроку хранения не создаётся: срок и порядок очистки не заданы.
- Снимок удаления содержит код, клиента, адрес, состав, цены, фото, историю и данные удалившего. Восстановление не создаёт новый заказ и не открывает заново отменённый. Снимок и `deleted_status` сохраняются после восстановления, все циклы удаления доступны в неизменяемом аудите.
- Заявка на удаление не скрывает заказ. При уходе из `new` она снимается как утратившая актуальность; первоначальная заявка остаётся в аудите. При фактическом удалении она тоже снимается. Отдельное согласование/отклонение заявок не требовалось.
- Проверка и изменение заказа выполняются под `FOR UPDATE`. Операции с вложениями блокируют родителя, поэтому удаление и изменение не расходятся между проверкой и записью.
- Исходный `staff_read` разрешал прямое чтение заказов всем активным сотрудникам через Supabase. В новой миграции у клиентских ролей отозваны права чтения операционных таблиц. RLS включён и на новых таблицах. Функции закрыты от PUBLIC/anon/authenticated; новые RPC работают с SECURITY INVOKER. Контекст аудита устанавливается в рамках транзакции, `p_user` получает только сервер из проверенного токена.
- Публичная ссылка возвращает одинаковое нейтральное 404 для удалённого, неизвестного и некорректного токена; причины и факт удаления не раскрываются. Приватные API и отслеживание используют `Cache-Control: no-store`.
- Профили не удаляются как часть удаления заказа; авторские UUID аудита намеренно без каскадного FK. Деактивация сотрудников сохраняет историю.

## Интерфейс и совместимость

- Для этапа 1 выбран лёгкий интерфейс на ES-модулях без сборки. Это соответствует исходному Express/static проекту и ограниченному объёму экранов. React/Vite, полноценная PWA и офлайн-очередь относятся к этапу 2. Расчёты цены и граф переходов в браузер не переносились.
- Новые UI-строки собраны в `public/i18n.js`, для причин есть `name_uz`. Узбекский перевод и переключатель пока не добавлены. Отображение дат — Asia/Tashkent, фильтры суток — UTC+05:00, новые телефоны требуют +998 и 9 цифр.
- Вход идёт через серверный Auth-адаптер с отдельным Supabase-клиентом; он не изменяет сессию service_role клиента БД. Access token хранится только в sessionStorage вкладки; пароль/refresh token не сохраняются. По истечении access token нужен повторный вход.
- Списки переведены на `{data,next_cursor}` с устойчивой сортировкой timestamp + id. Изменение формата явно описано в API. Поиск клиента по имени/телефону в существующем API ограничен 100 найденными клиентами; точный код заказа ищется напрямую. Полноценный масштабируемый поиск — отдельная задача.
- `Idempotency-Key` UUID обязателен для HTTP-создания. Один ключ сериализуется в SQL advisory lock, payload проверяется, повтор не создаёт новый заказ/аудит. Интерфейс сохраняет ключ до завершения отправки формы. После удаления заказа повтор по старому ключу отклоняется. Записи ключей хранятся бессрочно до утверждения политики хранения.
- Исходный lockfile выбирал Supabase JS 2.118.0, требующий Node 22, хотя проект и Render настроены на Node 20. Закреплена 2.78.0, совместимая с используемым API и Node 20; остальные прямые зависимости тоже закреплены, npm lock обновлён.
- Проверка npm audit выявила у исходной Zod 3 уязвимость потребления памяти GHSA-mrhx-c7xc-m3w5. Zod обновлена до 4.6.7; используемые схемы, обработка ошибок и интеграционные сценарии повторно проверены. Изменения API Zod сверены с [официальным руководством миграции](https://zod.dev/v4/changelog).

## Проверка и границы результата

SQL выполняется локально в PGlite, с исходной `0001`, настоящим pgcrypto, обеими новыми миграциями и ролями anon/authenticated/service_role. Для auth.users/storage используются минимальные тестовые схемы; данные рабочего Supabase не затрагивались. HTTP-тесты изолируют сетевой клиент; DOM-интеграция выполняет реальный код интерфейса, HTTP-маршруты и SQL RPC, заменяя только Auth/PostgREST чтение локальным адаптером.

Запуск Playwright/Edge в этой среде запрещён (`spawn EPERM`), поэтому визуальный браузерный тест не отмечается как пройденный. Реальный Supabase/Auth/Storage/PostgREST, Supabase advisors, восстановление облачной резервной копии и измерение <300 мс на 50 тыс. заказов здесь не выполнялись. Производственные ключи/проект не предоставлены; миграции и изменения подготовлены для применения, деплой не выполнялся.

При реализации проверены [документация SQL-функций Supabase](https://supabase.com/docs/guides/database/functions) и [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). Этапы 2–4 не начаты.

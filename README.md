# Ковёр CRM — этап 1

Существующий Express 5 / Supabase проект дополнен отказами клиентов, мягким удалением и восстановлением заказов. Расчёт цены и переходы статусов остаются в PostgreSQL. Реализован только этап 1; роли и рабочие места этапа 2, отчёты этапа 3 и интеграции этапа 4 не добавлялись.

## Что работает

- Отказ с причиной из справочника и обязательным комментарием. После приёмки в цех обязательны стоимость выполненных работ и сумма оплаты, принятой при отказе, в том числе нулевые.
- Оператор отменяет только `new` и может отправить заявку на удаление. Заказ остаётся в работе до решения администратора/руководителя.
- Администратор и `manager` переносят заказ в корзину с обязательной причиной и восстанавливают его с прежним статусом, кодом, клиентом, коврами, фото, историей и публичным токеном.
- Оплата или начатая стирка запрещают удаление. Возврат к раннему статусу и обнуление текущей оплаты этот запрет не снимают.
- В корзине сохраняется снимок данных на момент удаления. Есть фильтры по сотруднику, периоду и тексту причины.
- Все записи обычных списков и истории клиента исключают корзину. SQL-представления `active_orders` / `cancelled_orders` подготовлены для будущих отчётов. Отказы остаются в активных данных.
- Аудит содержит автора, роль, время, IP, состояние до и после действия. Запрещены `UPDATE`, `DELETE`, `TRUNCATE`, в том числе для администратора приложения.
- Веб-интерфейс подключён к API: вход, список и карточка, создание с SQL-превью цены, отказ, заявка на удаление, корзина, восстановление и аудит. Данные заказов в localStorage не хранятся. Интерфейс адаптируется под телефон, новые строки находятся в `public/i18n.js`.

## Запуск

Нужен Node.js 20+ (проверено в этой среде на Node 24.22.1). Версии зависимостей закреплены; `package-lock.json` предназначен для `npm ci` и существующего Render Blueprint.

1. Для новой БД выполните `0001_init.sql`. Для существующей БД повторно выполнять её нельзя.
2. Выполните `0002_manager_role.sql` **отдельным запуском SQL Editor**, затем `0003_order_lifecycle.sql`. Обе новые миграции допускают повторный запуск. `0003` выполняется транзакционно.
3. Создайте сотрудника в Supabase Authentication. Его профиль автоматически создаётся неактивным. Активируйте первого администратора:

   ```sql
   update public.profiles set role='admin', active=true, full_name='Администратор'
   where id=(select id from auth.users where email='you@example.com');
   ```

4. Для руководителя назначьте `role='manager'`, для оператора — `role='operator'`, обязательно `active=true`.
5. Скопируйте `.env.example` в `.env`, заполните `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Секрет находится только на сервере; браузер получает лишь access token своей учётной записи. Публичный ключ для этого интерфейса не требуется.
6. Запустите:

   ```sh
   npm ci
   npm test
   npm run dev
   ```

7. Откройте `http://localhost:3000`, войдите почтой и паролем сотрудника. `/health` проверяет HTTP-сервер. После истечения access token нужен повторный вход; автоматическое обновление сессии отложено до этапа 2.

На Render сохраняется `render.yaml`. Сначала примените миграции, затем разверните API и интерфейс одной версии; подробности в [инструкции эксплуатации](docs/operations.md). В этой работе облачная БД и Render не изменялись.

## API этапа 1

Все `/api/*`, кроме `/api/public/*`, требуют `Authorization: Bearer <access_token>` и активный профиль. Сервер проверяет токен через Supabase Auth и загружает роль из `profiles`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/public/login` | Вход сотрудника |
| GET | `/api/public/track/:token` | Публичный статус; для отсутствующего/удалённого заказа нейтральный ответ |
| GET | `/api/cancel-reasons` | Действующие причины отказов |
| POST | `/api/orders/:id/cancel` | Отказ с причиной, комментарием и суммами |
| POST | `/api/orders/:id/deletion-request` | Заявка оператора на удаление `new` |
| DELETE | `/api/orders/:id` | Только мягкое удаление, `{ "reason": "Дубликат" }` |
| GET | `/api/trash` | Корзина и фильтры |
| GET | `/api/trash/:id` | Карточка удалённого заказа и снимок |
| POST | `/api/orders/:id/restore` | Восстановление, тело `{}` |
| GET | `/api/audit-log` | Журнал с фильтром заказа/действия |

Остальные эндпоинты сохранены и описаны в [docs/api.md](docs/api.md). Важные изменения контракта: списки `/orders`, `/trash`, `/audit-log` возвращают `{data, next_cursor}`; `/status` больше не принимает `cancelled`; создание требует UUID в заголовке `Idempotency-Key`. Один ключ используется до получения определённого результата; повтор того же запроса возвращает тот же заказ, другой payload с тем же ключом отклоняется.

Пример отказа после приёмки в цех:

```http
POST /api/orders/K-1041/cancel
Authorization: Bearer <access_token>
Content-Type: application/json

{"reason_code":"condition","comment":"Материал не допускает обработку","completed_work_amount":20000,"payment_amount":0}
```

`payment_amount` — новая оплата **при отказе**, она прибавляется к уже принятой `paid_amount`. Это фиксация суммы для этапа 1; полноценная касса, способы оплаты, возвраты и чеки относятся к этапу 4.

## Проверка и результат

`npm test` выполняет SQL-функции и миграции в PGlite с настоящим расширением pgcrypto, проверяет HTTP API и полный пользовательский сценарий через DOM → HTTP → SQL. В этой среде прошли **26 тестов**. Рабочая Supabase БД для тестов не нужна.

Дополнительный `npm run test:browser` использует Playwright и установленный Edge; для Chrome можно задать `PLAYWRIGHT_CHANNEL=chrome`. В текущем окружении запуск браузерного процесса запрещён (`spawn EPERM`), поэтому визуальная проверка в браузере не подтверждена. Оставлен воспроизводимый тест; DOM-сценарий выполнен. Проверка сетевого PostgREST/Auth в вашем Supabase, нагрузочный замер на 50 тыс. заказов и восстановление реальной резервной копии потребуют подготовленного окружения.

Ручные сценарии: [docs/testing.md](docs/testing.md). Предлагаемое сообщение коммита:

```text
feat(orders): add cancellation, audited soft deletion and restoration
```

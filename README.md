# Ковёр CRM

CRM для стирки ковров и доставки: Express 5 / ESM, Supabase PostgreSQL/Auth/Storage, лёгкая PWA. Реализован базовый объём этапов 1–4. Расчёт цены, переходы статусов, финансовые ограничения, склад и начисления выполняются в PostgreSQL.

- Отказы, заявки на удаление, корзина, восстановление и неизменяемый аудит.
- Рабочие места оператора, диспетчера, водителя, цеха, руководителя и администратора; филиалы и история тарифов.
- Девять SQL-отчётов с фильтрами и Excel: формулы, условное форматирование, редактируемые диаграммы.
- Частичные оплаты/возвраты, касса водителя, квитанции, Payme/Click callback-адаптеры.
- Промокоды/накопительные скидки, акты с фото/дефектами и SMS-подтверждением, претензии/повторная стирка.
- Вместимость окон/районов/цеха, подсказки, группировка маршрута, печать QR, складские нормы и сдельные начисления.
- SMS/Telegram outbox, телефония, подписанные webhooks и формы, импорт CSV/XLSX, экспорт клиентов, теги/чёрный список/SLA.

## Заказ и замеры 0.7.0

Ковры — 12 000 сум/м², одеяло и тушак — по 30 000 сум/шт. В новом заказе оператор указывает вид и количество, структурированный адрес и регион. Замеры водителя и цеха сохраняются отдельно; цена ковров формируется водителем у клиента; замер цеха не меняет её автоматически. Водитель последовательно отмечает «Забрал» и «Передал цеху», сотрудник цеха — «Принял». Фотографии доступны в карточках заказа и клиента кнопкой «Посмотреть фото» и по умолчанию скрыты. Карта дорожного маршрута включается по желанию водителя. Доступны все регионы и 19 территорий Ферганской области. Подробности: [порядок работы и обновления](docs/booking-measurements.md).

## Запуск

1. Для рабочего запуска используйте Node.js 24; CI проверяет также 20/22. Примените миграции 0001–0012 по порядку, только ещё не выполненные. 0002_manager_role.sql и 0004_dispatcher_role.sql фиксируйте отдельными запусками/транзакциями перед следующими миграциями. Не переигрывайте старые миграции поверх более новой схемы.
2. Для первого запуска задайте BOOTSTRAP_ADMIN_EMAIL и BOOTSTRAP_ADMIN_PASSWORD (16–128 символов) в серверном окружении. Сервер создаст подтверждённую учётную запись и активного администратора. После успешного входа удалите пароль bootstrap из окружения; последующие старты не меняют пароль существующего администратора. При ручной настройке можно вместо этого создать пользователя в Supabase Auth и активировать его:

   ```sql
   update public.profiles set role='admin',active=true,full_name='Администратор'
   where id=(select id from auth.users where email='you@example.com');
   ```

3. Скопируйте .env.example в .env, заполните SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY. Ключ остаётся на сервере. Локальный запуск читает .env через npm run dev; npm start на хостинге получает переменные из окружения.
4. Выполните:

   ```sh
   npm ci
   npm test
   npm run dev
   ```

5. Откройте http://localhost:3000. В «Управление» администратор создаёт, редактирует, удаляет в архив и восстанавливает сотрудников, филиалы, тарифы, записи справочников и шаблоны. /health — живой процесс, /ready — доступность БД и схемы 10. Рабочий запуск через Render описан в [launch.md](docs/launch.md).

## Проверка и эксплуатация

94 сценария SQL/HTTP/DOM: цена, роли/филиалы, жизненный цикл, идемпотентность, отчёты, платежи, подписи, OTP, склад, SLA, импорт, права нового Supabase, первоначальный администратор, управление справочниками и ввод телефона. Девять Excel независимо пересчитаны и сверены с SQL. npm audit: уязвимостей не обнаружено на момент выпуска 0.5.2. npm run benchmark создаёт отдельную локальную базу с 50001 заказом и коврами; последний p95 SQL — 10.91 мс, без сети/PostgREST. HTTP p95 на целевом Supabase нужно измерить отдельно.

Браузерный E2E в этой среде недоступен (spawn EPERM). Перед рабочим выпуском выполните npm run test:browser, проверьте телефон/PWA, камеру и печать на вашем принтере. Вход использует access token в sessionStorage; после его истечения нужен повторный вход. Узбекский перевод можно добавить в словарь, готового перевода пока нет.

Провайдеры подключаются переменными окружения; контрактные тесты используют подставные ответы и не проводят платежи/рассылки. Для активации нужны аккаунты, проверка шаблонов и песочницы Payme/Click. Основной render.yaml сохраняет выбранный бесплатный web во Frankfurt, ждёт успешный CI и проверяет /ready. Worker не создаётся: автоматические SLA-задачи, напоминания и отправка outbox требуют отдельного процесса npm run worker. render.worker.example.yaml — отдельный платный ресурс, подключаемый только после выбора тарифа. У worker WORKER_SEND_ENABLED=false оставляет внешнюю отправку выключенной, но позволяет обрабатывать SLA/напоминания. Миграции не выполняются автоматически при старте приложения.
